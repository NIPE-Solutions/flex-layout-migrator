# Enterprise Shared Semantics and Rendering Design

## Purpose

Slice 4 makes target-neutral migration policy and project rendering explicit production owners. It moves responsive activation, directive-family grouping, dependency closure, and preservation decisions out of target adapters; narrows Tailwind and native CSS code to capability and output concerns; and routes the production pipeline through a concrete Render stage.

This is an internal refactor. For identical inputs and options, supported conversions, preserved source, diagnostics, generated bytes, ordering, reports, application behavior, and exit behavior remain unchanged.

The production route after this slice is:

```text
Discover -> Analyze -> Render -> compatibility validation/application
```

## Design Choice

Use an explicit semantic-plan-to-target-render transition. A target-neutral planner resolves what each source family means and whether the full contextual conversion is safe. A target renderer then decides whether that semantic family is supported and emits Tailwind classes or native CSS declarations and artifacts.

Rejected alternatives:

- Moving only the existing responsive helper would leave dependency and preservation policy distributed across adapters.
- Keeping `ConversionAdapter` as a policy-rich callback surface would preserve the current ownership ambiguity under new filenames.
- Cutting over Validate, Apply, reports, and presentation in this slice would combine slices 4 through 7 and make compatibility review too broad.

## Scope

This slice owns:

- target-neutral literal semantics for Flex-Layout families already represented in `src/flex`;
- directive-family identity and deterministic family ordering;
- responsive activation and precedence safety;
- local-layout and parent-layout contextual dependency closure;
- visibility/display and grid-parent dependency closure where those rules describe source semantics rather than emitted syntax;
- preservation decisions when a family is dynamic, ambiguous, incomplete, conflicting, or unsupported by the selected target;
- target capability decisions and target-specific diagnostics;
- Tailwind candidate rendering and conflicts;
- native CSS declaration rendering, generated class identity, and invocation-scoped rule registration;
- one invocation-scoped target session; and
- immutable `RenderedProject` production through a concrete Render stage.

This slice does not centralize source-edit validation, generated-template reparsing, output topology and collision validation, stylesheet merging, transaction work, report construction, or presentation. Those responsibilities remain behind named compatibility boundaries for slices 5 through 7.

No dependency or Changeset is added.

## Shared Semantic Model

Add a target-neutral semantic namespace outside `src/adapter`, rooted at `src/semantic`. Existing pure Flex semantic modules remain in `src/flex`; the new namespace coordinates them rather than duplicating their value parsers.

`DirectiveFamily` and responsive-family orchestration move from `src/adapter/responsive-family.planner.ts` to the semantic namespace. The shared planner consumes `LocatedFlexLayoutInput`, parsed element context, and a narrow target-capability contract. It returns ordered immutable family plans whose outcomes are:

- `planned`, carrying target-neutral family semantics and activation context;
- `review`, carrying an existing conservative diagnostic;
- `invalid`, carrying an existing invalid-value diagnostic; or
- `unsupported`, carrying a target-capability diagnostic.

The shared model retains source input identity and ranges. It does not contain Tailwind class strings, CSS declarations, generated class hashes, or mutable adapter state.

The semantic planner owns repeated dependency passes to a stable result. Adapters no longer expose `planElement`, `closePlanDependencies`, or `acceptPlans` as general policy hooks. Target-specific operations are instead named, narrow capabilities: eligibility, rendering of one resolved semantic family, output-equivalence where precedence safety depends on target output, conflict inspection, and invocation finalization.

Responsive breakpoint classification uses one invocation configuration and the existing `BreakpointCatalog`. The shared planner owns family grouping, base fallback coverage, overlapping-range safety, contextual layout selection, print activation semantics, and deterministic order. Target code owns only breakpoint syntax and explicit target limitations such as native CSS families that remain unsupported.

Tailwind-only source families—extended class/style composition, Grid, orientation/print syntax, and visibility utilities—still pass through the same semantic orchestration when dependency rules apply. Their semantic values may have only a Tailwind renderer, but unsupported native CSS behavior remains an explicit capability result rather than duplicated policy inside `CssAdapter`.

## Target Renderers

Replace the policy-rich `ConversionAdapter` surface with a renderer contract that cannot initiate project work or rewrite semantic decisions.

The Tailwind renderer owns:

- semantic-value-to-candidate conversion;
- responsive variant syntax;
- arbitrary property/value encoding;
- compiler-backed existing-class conflict detection;
- Tailwind-only extended, Grid, visibility, orientation, and print rendering; and
- byte-compatible candidate ordering and deduplication.

The native CSS renderer owns:

- supported-family capability declarations;
- semantic-value-to-declaration conversion;
- media context serialization inputs;
- deterministic generated class identity;
- rule deduplication and collision invariants; and
- invocation-scoped `OwnedCssRule` finalization.

Target renderers do not inspect unrelated directive siblings to decide semantic safety, perform source edits, read files, validate output topology, or publish reports. Target-specific conflicts may downgrade affected shared plans only through typed conflict results with the existing codes, reasons, and suggestions.

The current public adapter factory may remain as a compatibility constructor, but it returns one invocation-scoped semantic/render session. Any adapter aliases retained for tests are unreachable from the production authority graph and are scheduled for removal in slice 8.

## Render Stage

`RenderProjectStage` implements `RenderStage` and accepts one immutable `AnalyzedProject`. It owns one invocation-scoped target session supplied at CLI composition time. For each analyzed template in order, it:

1. preserves stored parse failures without calling semantic or target code;
2. builds element context from the stored parse result and located inputs;
3. requests one target-neutral semantic plan;
4. renders converted semantic families through the selected target renderer;
5. produces the same ordered conversion results and proposed template edit data; and
6. finalizes the target session exactly once after every template has been processed.

It returns `renderedProject({ analyzed, files, session })`, which enforces one-to-one ordered identity and freezes the handoff. A render failure prevents finalization-dependent downstream work; session reuse or double finalization fails closed as an internal invariant.

`CurrentMigrationPipeline` composes Discover, Analyze, and Render. Its downstream compatibility factory receives `RenderedProject`, not `AnalyzedProject` plus a live adapter, so `Migrator` can no longer invoke semantic planning, target rendering, or target-session finalization.

## Transitional Validation Boundary

The existing `AnalyzedFileMigrator` currently combines target planning with source-edit application, destination-state reads, and generated-template reparsing. This slice splits it into:

- Render-owned semantic and target planning; and
- a narrowly named compatibility edit validator used by `RenderProjectStage` to retain current `FileMigrationPlan` handoff shape.

The compatibility validator may apply planned edits, read a distinct destination to establish original artifact state, and reparse changed generated source. It cannot make semantic or target decisions. Slice 5 moves those duties into the concrete Validate stage and replaces the temporary Render output shape as needed.

Native CSS stylesheet reference collection and owned-stylesheet merging remain downstream because they depend on complete proposed project state. The renderer finalizes only immutable generated rules; it does not read or merge a stylesheet.

## Failure and Compatibility Rules

- Stored original parse errors remain data and produce the existing `template-parse-error` results without rendering.
- Dynamic bindings, invalid literals, ambiguous responsive precedence, incomplete dependencies, target limitations, and class conflicts retain their exact current status, code, reason, suggestion, source range, and order.
- A target limitation never changes shared semantic meaning and never causes another target to reject a supported conversion.
- Unknown semantic states, incomplete renderer results, identity mismatches, and session lifecycle violations fail closed as internal invariants.
- Relative invocation paths are remapped through the compatibility boundary exactly as in slice 3.
- Plan and write modes consume the same rendered handoff and cannot affect semantic or target decisions.

## Architecture Enforcement

Semantic TypeScript architecture tests must prove:

- responsive-family and dependency policy have one production owner outside `src/adapter`;
- `src/semantic` does not import Tailwind, native CSS, filesystem, edit, report, or transaction modules;
- target renderers do not import discovery, analysis-stage, filesystem-read, edit-application, report, or transaction authorities;
- only `RenderProjectStage` coordinates project-wide rendering and finalizes the target session;
- the downstream migrator receives `RenderedProject` and cannot import semantic planners or target renderers;
- native CSS artifact registration remains invocation-scoped and mutation does not escape the active render session; and
- Apply remains the sole project-write authority.

Architecture checks inspect resolved symbol provenance and call authority, with negative controls for test fixtures, ports, aliases, and unrelated same-named methods.

## Cross-Target Contract Tests

Add table-driven contracts for every Flex family supported by both targets. Each case supplies identical located inputs and element context, asserts the same semantic family and activation decisions, then separately asserts the existing Tailwind candidates and CSS declarations.

Additional cases prove intentional divergence:

- Tailwind-only Grid, visibility, extended class/style, orientation, print, and custom-breakpoint capabilities;
- native CSS `target-unsupported` outcomes;
- target-specific class conflict behavior;
- CSS generated-class and rule identity; and
- byte-compatible ordering and deduplication.

These tests complement rather than replace existing golden and compatibility fixtures.

## Performance and Verification

The workload counter must continue to prove:

- one discovery pass;
- one source read and one initial parse per selected template;
- one semantic planning pass per parsed template;
- one target render per converted semantic family;
- one target session and one finalization per invocation;
- no generated-template validation parse for unchanged templates;
- no stylesheet parse when the target cannot produce a stylesheet; and
- no project writes in plan mode.

No wall-clock improvement is claimed without five comparable samples. Structural counter changes are documented against the checked-in baseline.

Implementation follows strict red-green-refactor cycles. Acceptance requires focused semantic, renderer, session, Render-stage, continuation, architecture, and counter tests; all existing parity and golden tests; packaged CLI execution; `npm run clean && npm run verify`; and a clean tracked worktree. An independent whole-branch review is required before pull-request handoff.

## Delivery and Removal Map

This slice adds the shared semantic owner and concrete Render stage, redirects `CurrentMigrationPipeline` through it, and removes semantic/render/session ownership from `Migrator` and target adapters.

The compatibility edit validator is removed by slice 5. The downstream migrator retains stylesheet planning, validation, transaction, and reporting until their named slices. Adapter and migrator aliases that become unreachable are deleted in slice 8 unless deleting them here is mechanically safe and does not broaden the review.

## Acceptance Criteria

1. The CLI-facing route executes Discover, Analyze, and concrete Render stages in order.
2. Target-neutral responsive and dependency policy has one owner outside target adapters.
3. Tailwind and native CSS renderers consume resolved semantics and own only capability, syntax, artifacts, and target conflicts.
4. `RenderedProject` is ordered, immutable, and finalized by exactly one invocation-scoped session.
5. Downstream compatibility code cannot perform semantic planning, target rendering, or session finalization.
6. Cross-target contracts prove shared semantics and intentional capability differences.
7. Public outputs and all structural workload guarantees remain compatible.
8. Full verification and packaged execution pass.
